# Assumptions & Data Gaps

The Phase 3 warehouse parquet set only exposes per-booking grain
(`fact_booking`) plus dimension tables — no pre-aggregated daily marts, no
restaurant/staffing data at all. A few inputs the spec calls for don't exist
as real columns anywhere in this project. Each is clearly synthetic/derived,
not measured. Items 8–10 below are new to Phase 4; see also
[reports/final_phase4/known_limitations.md](../reports/final_phase4/known_limitations.md)
for the consolidated, phase-level summary.

1. **Room type** (`data/warehouse/dim_room_type.parquet`, originally derived
   from `data/raw/room_type_dim.csv`) — Standard / Deluxe / Suite +
   `base_price_multiplier`, since the source hotel-bookings dataset only has
   single-letter room codes with no published mapping to real room classes.
   Cross-joined onto pricing rows in
   `src/features/pricing_features.py::add_room_types`.
2. **Events / holiday calendar** (`data/raw/events_holiday_calendar.csv`) —
   synthetic seed: real US public holidays plus a fabricated set of
   recurring "local events," generated once and stored as a static CSV
   (2023–2026). Joined by date in `src/features/calendar_features.py`.
3. **Pricing "demand" input** — no direct demand measure exists, so
   `demand_index = occupancy_pct * (total_revenue / revenue_7day_avg)` is
   used as a proxy in `src/features/pricing_features.py::add_demand_index`
   ("demand is elevated when both occupancy and revenue momentum are high").
4. **Restaurant "expected quantity"** — the synthetic restaurant seed (see
   item 9) has per-meal *revenue* (breakfast/lunch/dinner) and a day-level
   `items_sold`, but no per-meal item count. Quantity is approximated as
   `items_sold * (meal_revenue / total_revenue)`, cross-checked against
   `meal_revenue / avg_item_value` (see
   `src/features/restaurant_features.py::derive_meal_quantities`; >20%
   divergence between the two estimates is logged).
5. **Churn label** — no churn flag exists in the warehouse. Defined as a
   recency cutoff: `churn = 1` if `(snapshot_date - last_stay_date).days >
   CHURN_WINDOW_DAYS` (default 180, configurable via `.env`) **and**
   `lifetime_bookings >= 1` (guests who never stayed are excluded — churn
   isn't meaningful for them). See `src/features/churn_features.py::label_churn`.
6. **Churn risk-level thresholds** — business-defined defaults, not fit
   from data: probability `< 0.3` → Low, `0.3–0.6` → Medium, `> 0.6` → High
   (`src/config/constants.py::churn_probability_to_risk_level`).
7. **Season mapping** — standard meteorological seasons by month
   (`src/config/constants.py::MONTH_TO_SEASON`), not hotel-specific
   high/low season definitions (which would require booking-price
   elasticity analysis out of scope for this phase).
8. **Room capacity per hotel** (`src/features/occupancy_aggregation.py::
   ASSUMED_TOTAL_ROOMS`) — the source dataset has no room-inventory count
   anywhere, so `occupancy_pct` is computed against a fixed, illustrative
   capacity constant per hotel (Resort Hotel: 200, City Hotel: 300), not a
   measured value.
9. **Restaurant daily revenue/quantity**
   (`data/raw/restaurant_daily_synthetic.csv`, generated by
   `src/pipelines/synthetic_data.py::generate_restaurant_daily`) — no
   restaurant order data exists anywhere in this project. Values are
   deterministically generated (seeded RNG, reproducible) from real derived
   daily occupancy: `revenue = base_rate[meal] * occupied_rooms *
   day_of_week_multiplier * (1 + small_noise)`. This is fabricated training
   data, not a proxy for a real signal — treat all restaurant model outputs
   as illustrative only.
10. **Staffing daily headcount**
    (`data/raw/staffing_daily_synthetic.csv`, generated by
    `src/pipelines/synthetic_data.py::generate_staffing_daily`) — no staff
    attendance data exists anywhere in this project. Values are
    deterministically generated from real derived daily occupancy:
    `present_employees ≈ ratio[department] * occupied_rooms *
    day_of_week_multiplier`, same fabrication caveat as restaurant data.
11. **Churn training/prediction snapshot date** — the canonical dataset only
    covers 2015-07-01 to 2017-09-13. `label_churn`'s `snapshot_date` defaults
    to the real system clock, which would make every guest's recency exceed
    `CHURN_WINDOW_DAYS` and collapse the label to a single class. Both
    `src/pipelines/churn_pipeline.py` and `src/prediction/predict_churn.py`
    instead anchor `snapshot_date` to one day after the guest data's own
    `last_stay_date` max — consistent between training and prediction, but
    not the real "today."
12. **Occupancy forecast anchor date** — for the same reason as item 11,
    `src/prediction/predict_occupancy.py::forecast_occupancy` anchors its
    forecast start date to the day after the trained Prophet model's own
    training data range (`model.history["ds"].max()`), not the real system
    clock — forecasting from "today" against a model trained only on
    2015-2017 data would extrapolate roughly a decade forward and produce
    meaningless (even negative) occupancy values.
